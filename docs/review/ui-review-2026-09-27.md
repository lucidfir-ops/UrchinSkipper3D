# UI review — September 27, 2026

Review by the accessibility/interaction agent, separately from the HUD and menu presentation authors. This agent implemented the stable touch/assistance views; its assessment of those two views is therefore implementation verification, not an independent visual opinion. The HUD, title, Settings, Pause, fleet, starter purchase, crew and office screenshots were reviewed independently.

## Evidence and provenance

Local evidence is under `test-results/ui-overhaul/`. The original `baseline` folder was renamed `early-integration`, with a provenance note: those captures were made during concurrent edits and mix old and incomplete new presentation. They are **not a clean before-state** and do not establish a before/after comparison.

`iteration1` and `iteration2` contain production-build captures from the full interaction script. `hud-pass` contains the HUD author's separate follow-up captures. The reviewer opened the images at their actual viewport sizes using the image viewer rather than evaluating filenames or DOM geometry alone. Reviewed sizes include 1280×800, 390×844 and 844×390. Later captures supersede earlier ones where described below.

`accessibility-final` and `accessibility-firefox` contain this reviewer's successful production-build interaction captures and JSON receipts, made against port 5186. Chromium and Firefox both passed. An earlier attempt against a stale production server failed to start because that server retained compressed HTML referencing superseded asset hashes; restarting the server corrected the test setup. That attempt was not counted as a game pass or a game regression.

## Problems found and changes required

- Early HUD screenshots were unacceptable: gauges were solid black, a compass was cropped, crew portraits filled huge panels and labels collided. The missing replacement stylesheet was restored. Later production screenshots render complete instruments, named diver cards and clear numeric readings.
- The first portrait tutorial placed Frank directly over the boat. Later HUD captures move the followed view within the authorized orthographic tutorial framing so the boat is visible above the lesson. The initial overlapping control-help and action regions were referred back for further adjustment.
- Early landscape HUD captures allowed the bottom controls to overlap the boat. Later captures keep the vessel between the instrument row and control area. The first follow-up still allowed Frank's buttons to overlap the action row and was rejected for another pass.
- The fleet's first redesigned cards had text wrapping around vessel images, producing joined fragments such as tank/price/action text. The latest reviewed production cards use a consistent image-and-copy composition and readable price/ownership hierarchy.
- Starter purchase initially wasted most of the right panel and repeated its primary action. Its replacement presents the two hulls with a selected-vessel explanation and a distinct purchase action. The career-difficulty selector was still partly below the visible list at 1280×800 in iteration2; the reviewer requested that it move before the hull cards so mode choice is visible before purchasing.
- Assistance switches previously rebuilt their DOM when focus changed, which could remove a pressed target before release. Stable mounted rows now update only their state and explanation. Both browsers passed a 300 ms held mouse press, DOM-identity assertions and native-focus checks.
- On phones, a distant explanation panel was not a useful way to explain a switch near the top of a long list. Option labels now disclose help immediately within the same row, with `aria-expanded` and `aria-controls`; controller focus also updates the persistent explanation.
- Touch sliders initially measured only 30.39 physical CSS pixels high at the default phone scale. Their interactive areas now meet 44 pixels, as do the touch menu buttons in both tested orientations. Independent control size/opacity, a persistent live preview and separate information-layout switches are retained.

## Interaction verification

The committed `scripts/ui-accessibility-checks.js` reproduces these checks in Chromium or Firefox:

- Natural title → tutorial → assistance/settings paths, with Back returning to the opening context.
- Switch nodes survive focus changes and a held pointer click; the pressed switch receives native focus, changes once and updates the Custom-preset status.
- Sliders remain mounted while dragging. The opacity step buttons adjust by five points; reset restores 100% control size and opacity.
- Touch mode, Adjust UI and Show information switches work; browser-local touch/opacity preferences survive reload.
- Touch menu buttons and sliders measure at least 44×44 physical CSS pixels at 390×844 and 844×390; no page-wide horizontal overflow.
- The phone assistance explanation is visible adjacent to the selected option.
- No browser page errors or failed resources during either successful production run.

Existing settings/preset/navigation tests also passed. The main agent separately owns the complete keyboard/controller voyage and regression/build acceptance receipts.

## Assessment and limits

The latest reviewed desktop menus share a coherent typography, spacing, focus and panel system. Settings and Pause are grouped by purpose, crew portraits lead to readable details, and vessel cards expose ownership/price without accidental purchasing. Desktop HUD readings occupy predictable edges and preserve a clear working-water area. Realistic screenshots use identity-only diver selectors and omit the additional Easy assistance; All Off removes the information panels.

Phone control density is intrinsically high because the existing independent helm, two divers and working actions remain available. Instrument headline values are readable, but small gauge graduations and explanatory captions are still secondary detail at a 390-pixel width. UI Scale and saved layout controls remain necessary accessibility tools; these screenshots do not prove every possible saved arrangement is overlap-free.

This is not a formal WCAG conformance audit. Physical Xbox/Steam Deck input, actual phone touch accuracy and performance, Safari, screen-reader usability of the complete game, and long-session visual fatigue remain unverified. Synthetic controller events and touch-capable browser contexts cannot establish those physical-device results. Final phone/landscape overlap fixes and the starter-difficulty relocation require review of their later captures before closing those specific findings.
